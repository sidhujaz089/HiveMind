ONE file: projects/local-inference/coder.py. Make a reply that ended at the output token cap (done_reason == "length") impossible to accept as a complete answer, on EVERY path, by editing two functions and nothing else. (1) In ask(): both branches currently guard the truncation check behind the per-caller flag -- the native branch reads `if raise_on_length and d.get("done_reason") == "length":` and the gateway branch the same form on ask.last. Drop the `raise_on_length and` condition in both, so a length-cut reply always runs the existing window_full() test first (keep raising WindowFull, with prompt_eval_count and the window, when window_full() says the window is what filled) and otherwise raises Truncated. Keep ask.last fully populated before the raise -- done_reason, thinking, content, eval_count -- so the trail records what the model actually said; on the gateway branch keep the existing assignment of ask.last["content"] from the stripped reply. Keep accepting the raise_on_length keyword and ignore it, and say so in the docstring: it is now advisory, and a length-cut reply is a truncation for every caller. (2) In finish_truncated(): pass raise_on_length=True on the call to ask_fn, and wrap that call in a try/except for Truncated so a salvage that is ITSELF cut off returns an EMPTY answer, never the fragment. The except must RECORD what it caught: return the exception's own token count and seconds as the tokens and seconds, put the word 'truncated' in the note, and do not let the note claim it resumed from the whole reasoning. The empty string is the point -- a second silence is not a verdict, so a cut-off salvage must never reach the caller as a usable answer.

WHY: Both truncation checks in ask() are gated behind a per-caller opt-in: the guard in the native branch is `if raise_on_length and d.get("done_reason") == "length":` and the gateway branch repeats the pattern on ask.last. A caller that leaves raise_on_length at its default is RETURNED a reply that ran out of budget mid-generation, with no signal that it is incomplete. The dispatch that filed this task is such a caller: the file-serving branch logged 'asked for 1 file(s), gave 1 new (232 tok, 12s)' for a file the brief required to be 114+ lines, and the harness accepted that reasoning-starved fragment as valid file content -- no done_reason=length detected, no re-ask with reasoning off, and the stub broke the pre-existing suite in attempts 1 and 3. Both must be fixed in ask() and finish_truncated() themselves, not at one call site, because every present and future caller inherits the default.
