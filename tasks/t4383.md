WHY IT IS STRUCTURAL, NOT BAD LUCK: the live checkout is simultaneously (a) the thing services append runtime rows to, (b) the tree a merge must update, and (c) the tree check_workspace reads. Any agent merging while the services are writing is racing them, and with N agents the race is guaranteed rather than improbable. auto_merge.py already takes an flock and t3196 already widened its eligibility to judge every queued branch, so the lock and the queue EXIST -- what does not exist is a rule that makes main have exactly ONE writer at a time, and a merge step that treats machine-written ledgers as records rather than as conflicts.

THE BUILD: (1) one merge lock, held across the whole merge+gate critical section, so two agents cannot interleave a merge and a gate run; (2) inside that lock, commit the machine-written runtime rows as their own `chore(workspace): records` commit BEFORE merging, which is the same separation L-090 asks for and turns today's abort into a normal step; (3) record the gate's verdict per merge (the bar Jas set -- 0 failed after each merge -- as a row, not as a promise), and refuse the merge on a non-zero. No new queue: reviewq.py lists the branches and auto_merge.py merges them; this is a wrapper around what exists.

ORACLE, and it has to be able to fail: two merge attempts racing produce two serialised merges and main never observes an interleaved state; a live checkout dirty with runtime rows merges successfully and the rows end up committed in a records commit rather than abandoned or carried; a gate FAIL inside the lock refuses the merge and writes a row saying so. Red proof: today's first attempt aborted -- that is the failing case, and it is reproducible by touching a ledger on the merge target first.
